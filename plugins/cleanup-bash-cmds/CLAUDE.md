# Cleanup Bash Cmds Plugin

The cleanup-bash-cmds plugin lives at `plugins/cleanup-bash-cmds/`. Commands containing a heredoc (`<<`/`<<-`, anywhere in the tree, including inside `$()`) are DENIED outright via `permissionDecision: "deny"`. Commands invoking `perl` are likewise DENIED (effective command name matching `^perl[0-9.]*$`, so `perl5.36`, `command perl`, and `\perl` all count. `perl` as an argument like `grep perl`/`perlcritic`, `command -v perl`, and `perl` inside a command substitution such as `echo $(perl -e 1)` are NOT denied). Any invocation of the four in statement position (same walk as the perl deny -- pipes, `&&`/`||`, compounds, function bodies. `git rm --cached` only unstages and passes through untouched), and an `rm` carrying a flag the rewrite will not translate (`reason="rm_flag"`). A plain `> file` redirect is deliberately NOT denied. Otherwise it rewrites every `rm` to `recycler trash` so deletion is non-destructive by construction. The `-delete` primary of `find` is rewritten in place to `-exec recycler trash {} +`, the command its deny already named. It stays in place, so every other primary keeps its position in find's expression grammar. A zero-size `truncate` is REWRITTEN the same way (`truncate -s 0 f` -> `recycler trash f`, every spelling of the size flag, `--` re-emitted in front of a dash-leading name). Emptying a file and moving it to the recycle bin lose the same content, and only one of them can be undone. The deny already named that exact command, so it spent a round trip on a rewrite the hook had worked out. Another flag still denies. `-r RFILE` names a reference file rather than a target, so dropping the flag and keeping its value recycles a path the command never touched. That rewrite is tree-wide and explicitly NOT last-statement-anchored (`rm -f a.js && node b.ts` -> `recycler trash a.js && node b.ts`, the incident shape. `recycler` is a hard dependency of the REWRITTEN COMMAND, not of the hook. It is emitted as a bare word (PATH resolves it) with no probe, no `command -v`, and no fallback to `rm`. Never inside `$(...)`/`<(...)` captures), rewrites a trailing stdout file redirect into `| tee file` on that same final statement only (`>> file` -> `| tee -a file`. `/dev/` targets, process substitutions, and multi-stdout-redirect statements excluded. Everything else becomes `sleep 3`, assigns/redirects preserved), and removes constant narration `echo`/`printf` whose stdout reaches the terminal (not feeding a pipe. Not inside `$()`/`<()`/`>()`/assignment captures, FuncDecl bodies, or coprocs. A format directive is not what distinguishes the two. The effective-command resolver sees through `command`/`builtin`/leading-`\`/quoting wrappers (`command echo`, `\printf`, `"printf"`, `command command echo` all resolve) while `command -v/-V X` is a lookup that triggers nothing. Strictness settings the user wrote (`set -e` etc.) are never removed. After regeneration the hook re-parses the cleaned command and fails open. The hook is fully silent by design: every rewrite emits ONLY `updatedInput` + `suppressOutput: true` -- never a `systemMessage` or `additionalContext` (a visible hook message lets the model blame the hook for its own command mistakes). Only the denies return a reason (heredoc points at the Write/Edit tools, perl says it is banned, file_read points at the Read tool, and the destructive-form denies each name the `recycler` alternative that works). shfmt operator numbers are version-dependent, so the hook probes them at runtime. Missing tools or unparseable commands fail open (no pipefail injection into anything unparseable).

It also rewrites the GitHub Actions reads. Every Actions read in this environment goes through `gh wait-ci`. The `gh` shim refuses `gh run` and `gh pr checks` at run time. Each of those spellings is a guaranteed failure that costs a whole tool call. Seven forms carry the same meaning on both sides and are rewritten (`gh run view <id> --log-failed` -> `gh wait-ci log <id> --failed`, `--log` -> `gh wait-ci log <id>`, bare view -> `gh wait-ci view <id>`, `run watch` -> a bare `gh wait-ci <id>`, `run rerun`, `run list` -> `runs`, `pr checks` -> `checks`). Everything else is left alone rather than guessed at. The shim already refuses it with the full mapping. A wrong guess replaces a precise message with a command that asks a different question. The run id must be a static run of digits, so `gh run view "$ID"` passes through. A trailing POSITIONAL blocks the rewrite, while trailing FLAGS AND THEIR VALUES survive. `gh pr checks 42` names one pull request where `gh wait-ci checks` reads the current branch. `--branch main` is a value and not a subject. Re-firing is impossible by construction: every output carries `wait-ci` in the subcommand slot, which matches none of the arms.

- **Hook script**: `plugins/cleanup-bash-cmds/hook.sh` -- orchestration (extract command, probe ops, parse, transform, regenerate, emit)
- **AST transform**: `plugins/cleanup-bash-cmds/transform.jq` -- all rewrite rules
- **Tests**: `plugins/cleanup-bash-cmds/tests/run-tests.sh` -- self-contained runner (bootstraps a pinned shfmt if the machine lacks one). CI runs it via the plugin `justfile` `prebuild` recipe
- **Plugin config**: `plugins/cleanup-bash-cmds/.claude-plugin/plugin.json` -- PreToolUse/Bash matcher invoking `hook.sh`

For rewrites the hook emits `hookSpecificOutput.updatedInput` WITHOUT a `permissionDecision`, so the normal permission flow evaluates the rewritten command (it does not auto-allow). Only the bans emit a `permissionDecision` (`"deny"` + reason). The debug channel is `CLEANUP_BASH_CMDS_LOG`: every rewrite is logged with the rules that fired (`REWRITE ... rules="grep,pipefail"`.

The other half lives in the `no-work-loss` plugin. It refuses a `Write` over an existing path, and over one sitting in the recycle bin. It also refuses the Bash routes that change file content outside the edit tools. See `plugins/no-work-loss/CLAUDE.md`.
