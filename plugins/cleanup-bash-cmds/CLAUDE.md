# Cleanup Bash Cmds Plugin

The cleanup-bash-cmds plugin lives at `plugins/cleanup-bash-cmds/`. It is a PreToolUse hook in bash + jq + shfmt (cross-platform, no compiled binary) that inspects and rewrites Bash tool commands before execution by parsing them: `shfmt --to-json` produces the syntax tree, a jq program transforms it, and `shfmt --from-json` regenerates the command. Commands containing a heredoc (`<<`/`<<-`, anywhere in the tree, including inside `$()`) are DENIED outright via `permissionDecision: "deny"` -- herestrings (`<<<`), strings containing `<<EOF`, and `$((x << 2))` bit shifts are not affected. Commands invoking `perl` are likewise DENIED (effective command name matching `^perl[0-9.]*$`, so `perl5.36`, `command perl`, and `\perl` all count; `perl` as an argument like `grep perl`/`perlcritic`, `command -v perl`, and `perl` inside a command substitution such as `echo $(perl -e 1)` are NOT denied). Reading a file with `cat`/`head`/`tail`, or with a `sed` that suppresses automatic printing (`-n`, a cluster containing n such as `-ne`, `--quiet`, `--silent`) and names a file, is likewise DENIED (reason points at the Read tool) -- a `sed -n '3p' f` is the same file read as `head`, in the spelling that used to walk around the rule, while a `sed` WITHOUT that suppression transforms its input and is untouched. Any invocation of the four in statement position (same walk as the perl deny -- pipes, `&&`/`||`, compounds, function bodies; effective-command resolution applies, so `command cat` and `\head` count) naming at least one static file operand that is not a `/proc`, `/sys`, or `/dev` pseudo-file; flag values are understood (`head -n 20 /proc/meminfo` is exempt -- `20` is a value, not a file), and stdin/pipe plumbing (`cmd | head -5`, `cat -`), process substitutions (`cat <(cmd)`), expansion operands (`cat "$F"`), and word-internal uses (`x=$(cat f)`) are NOT denied. Destructive forms that cannot be rewritten into a move-to-recycle-bin are DENIED with the alternative that can: `shred`/`srm` (unrecoverable by design, no alternative offered), `find ... -delete` (-> `find ... -exec recycler trash {} +`), `git rm` on the working tree (-> `recycler trash <path> && git add -A`; `git rm --cached` only unstages and passes through untouched), `truncate -s 0`/`--size=0` (-> `recycler trash <path>`), and an `rm` carrying a flag the rewrite will not translate (`reason="rm_flag"`). A plain `> file` redirect is deliberately NOT denied -- stdout redirection is overwhelmingly ordinary output routing, `tee_rewrite` already owns that shape, and denying it would fight the plugin's own behavior and fire constantly on non-deletions (so `: > file` still truncates: a known, accepted gap). Otherwise it rewrites every `rm` to `recycler trash` so deletion is non-destructive by construction -- the target lands in the platform's native recycle bin (FreeDesktop trash can, macOS `~/.Trash`, Windows Recycle Bin) where `recycler list` finds it and `recycler restore` puts it back. That rewrite is tree-wide and explicitly NOT last-statement-anchored (`rm -f a.js && node b.ts` -> `recycler trash a.js && node b.ts`, the incident shape; loop bodies, function bodies, `if` branches, and `$( )` captures are all reached), and `xargs rm` gets its OWN case because there `rm` is an argument word the effective-command resolver never sees (xargs' value-taking flags `-n N`/`-I R`/`-P N`/... are understood so the utility word is located correctly). Flags `-r`/`-R`/`--recursive`, `-f`/`--force`, `-v`/`--verbose`, `-i`/`-I`/`--interactive` and `--` are dropped (bundled clusters like `-rf`/`-rfv` count only when EVERY letter is droppable; `--` is re-emitted in front of the targets when any target is dash-leading, so `rm -- -weirdname` stays correct), while any other flag (`-d`, `--one-file-system`, `--no-preserve-root`, `--nonsense`) takes the `rm_flag` deny rather than being guessed at. The rule never re-fires on a call that is already `recycler` (the transform runs to a fixpoint) and only ever emits `trash`, never `purge`/`empty`, which are themselves permanent deletes. `recycler` is a hard dependency of the REWRITTEN COMMAND, not of the hook: it is emitted as a bare word (PATH resolves it) with no probe, no `command -v`, and no fallback to `rm`, so a runtime failure (permissions, unreachable bin) surfaces as a visible error with the file still on disk -- and note `rm -f nonexistent` (silent success for real rm) becomes a visible error, the same fail-loud posture as the rest of the hook. It also strips ALL `2>/dev/null` stderr suppression anywhere in the tree (Redirect nodes only -- quoted strings and fds like `12>/dev/null` are structurally safe), rewrites `docker compose restart` to `docker compose up -d --force-recreate` wherever it executes (a restart bounces the existing containers, so edits to `compose.yaml` are not applied -- see the Docs Plugin section, whose `docker-compose` skill teaches the same rule at authoring time), kills any chain of trailing `| head ...` / `| tail ...` / `| sed -n <line select>` pipeline stages on the FINAL top-level statement only (the rightmost `&&`/`||` leaf -- mid-script limiting pipes are deliberate and preserved; never inside `$(...)`/`<(...)` captures), rewrites a trailing stdout file redirect into `| tee file` on that same final statement only (`>> file` -> `| tee -a file`; `/dev/` targets, process substitutions, and multi-stdout-redirect statements excluded; mid-script `> file` preserved), prepends `set -o pipefail` unless the command already enables it, removes trailing `2>&1`, trailing `|| true`, and trailing `| grep` (final-statement-anchored as well), caps every `sleep` anywhere in the tree at 3 seconds (all-literal GNU durations summing <= 3 are kept; everything else -- over-cap sums, `$VAR`/`$( )` args, `infinity`, junk, zero args -- becomes `sleep 3`, assigns/redirects preserved), and removes constant narration `echo`/`printf` whose stdout reaches the terminal (not feeding a pipe; not inside `$()`/`<()`/`>()`/assignment captures, FuncDecl bodies, or coprocs; no stdout redirect -- pure-stderr `2>` redirects allowed) by rewriting the whole command to the no-op `:` (no output, exit 0, surrounding structure and redirects intact) -- `echo` when every argument is constant (glob/tilde/expansion args don't count), `printf` on the same test as `echo` -- every argument after the command word is constant, so `printf -- 'x'`, `printf '%s\n' hi` and `printf a b c` all go, while ANY expansion (`printf 'rc=%s\n' "$?"`) keeps it, because an expansion is what makes a printf carry data rather than narration. A format directive is not what distinguishes the two, which is what the old one-static-arg-with-no-`%` rule got wrong: `printf '%s\n' hi` prints a fixed string and was the spelling that walked around the `echo` rule; the effective-command resolver sees through `command`/`builtin`/leading-`\`/quoting wrappers (`command echo`, `\printf`, `"printf"`, `command command echo` all resolve) while `command -v/-V X` is a lookup that triggers nothing. Strictness settings the user wrote (`set -e` etc.) are never removed. After regeneration the hook re-parses the cleaned command and fails open -- emits no rewrite -- if it somehow has fewer top-level statements than the original (belt-and-braces guard against ever executing a truncated command). The hook is fully silent by design: every rewrite emits ONLY `updatedInput` + `suppressOutput: true` -- never a `systemMessage` or `additionalContext` (a visible hook message lets the model blame the hook for its own command mistakes); only the denies return a reason (heredoc points at the Write/Edit tools, perl says it is banned, file_read points at the Read tool, and the destructive-form denies each name the `recycler` alternative that works). shfmt operator tokens are version-dependent (numbers before shfmt 3.14, strings from 3.14 on), so the hook probes them at runtime and accepts either representation; missing tools or unparseable commands fail open (no pipefail injection into anything unparseable).

- **Hook script**: `plugins/cleanup-bash-cmds/hook.sh` -- orchestration (extract command, probe ops, parse, transform, regenerate, emit)
- **AST transform**: `plugins/cleanup-bash-cmds/transform.jq` -- all rewrite rules
- **Tests**: `plugins/cleanup-bash-cmds/tests/run-tests.sh` -- self-contained runner (bootstraps a pinned shfmt if the machine lacks one); CI runs it via the plugin `justfile` `prebuild` recipe
- **Plugin config**: `plugins/cleanup-bash-cmds/.claude-plugin/plugin.json` -- PreToolUse/Bash matcher invoking `hook.sh`

For rewrites the hook emits `hookSpecificOutput.updatedInput` WITHOUT a `permissionDecision`, so the normal permission flow evaluates the rewritten command (it does not auto-allow); only the bans emit a `permissionDecision` (`"deny"` + reason). The debug channel is `CLEANUP_BASH_CMDS_LOG`: every rewrite is logged with the rules that fired (`REWRITE ... rules="grep,pipefail"`; the narration/sleep/rm rules log as `narration_remove`/`sleep_cap`/`rm_recycle`), denies as `DENY ... reason="heredoc"`, `"perl"`, `"file_read"`, `"rm_flag"`, `"shred"`, `"find_delete"`, `"git_rm"`, or `"truncate_zero"`, and statement-count fail-opens as `GUARD ... reason="stmt-count"`.

The other half of this lives in the `no-work-loss` plugin, which refuses a `Write` over an existing path (and over one sitting in the recycle bin) and refuses the Bash routes that change file content outside the edit tools -- see `plugins/no-work-loss/CLAUDE.md`.
